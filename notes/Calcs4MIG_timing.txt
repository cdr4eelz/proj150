Since Arty's external DDR3 is 16-bits wide, that establishes the number of bits/bytes that comment
    in a burst of 8 (the only burst option in MIG). 16 bits x 8 burst-units = 128 bits.
    First, the MIG read/write data widths are 64-bit (plus a mask on the side for writes).
    The 128 bits comes/goes by way of 64-bit buses (read/write) necessitating two strobes.
    One command to read sends back two 64-bit responses. One write requires 2 64-bit inbound.
    For compatibility, the CDC FIFOs between CPU and MIG are kept at their original 128-bit width.
    One job of the MIGAdapter is to break one 128-bit write value (and mask) into two 64-bit values.
    Likewise, a reads assemble a 128-bit response to FIFO from two 64-bit responses from MIG.
    Then, since old behavior was to receive/send two 128-bit values per one command/request to MIG.
    Therefore, MIGAdapter turns one command into two, consuming two 128-bit write values or
    returning two 128-bit read values (which the old logic translates to/from 256-bits).
    Technically, the MIG docs indicate that for a write, the write data pulses (64-bit each)
    must arrive at the MIG either before, during, or two clocks behind the write command arrives
    at the MIG interface. The current MIGAdapter currently sends them after the command and
    is working fine, but it should be changed to reverse the order in case a rare circumstance
    makes the Write FIFO lag behind the Command FIFO. The read FIFO has no such circumstance
    and its 2 MIG -> 1 FIFO value functions as a separate state machine from the Command/Write
    signals. Ideally, the MIGAdapter would count count the strobes in and out, to detect a
    mis-match/loss/stall (overflow/underflow) and at lease generate a debug signal. The Cache
    module does have a counter that detects when a read response doesn't arrive within a
    reasonable clock count.
